# Сбор живой речи для v0.2 (протокол и runbook)

Единственный блокер приёмки wake-word v0.2 — датасет живой речи
(training/README.md: ≥500 произнесений «Omni» от ≥20 дикторов, ≥10 ч
фонов, ≥200 трудных негативов). Ниже — как его закрыть без студии:
телефон, диктофон, целевое устройство, пара вечеров.

v0.1 обучена ТОЛЬКО на синтетике Piper TTS: реальные акценты, реверберация
комнат, шум носимого устройства не представлены (OMNI_V0.1_REPORT.md,
«Известные ограничения»). Протокол построен вокруг закрытия именно этих дыр.

## 1. Языки и акценты (топ-3 целевых рынка)

Локали приложения: `values` (English), `values-ru` (Русский), `values-tk`
(Кыргызча). Минимум ≥500 должен покрывать ВСЕ ТРИ языка:

| Язык | Минимум позитивов | Пояснение |
|---|---|---|
| Русский | ≥150 | произношение «омни» (твёрдое/мягкое «мь», ударения) |
| English | ≥150 | акценты: нативный EN + EN с неродным акцентом |
| Кыргызча | ≥150 | «Омни» — как реально скажет носитель tk (проверить с носителем) |

Плюс 1–2 диктора с выраженным неродным акцентом любого из трёх языков
(сценарий «пользователь не носитель языка приложения»).

Один диктор = одна метка `--speaker` (латиницей: `ivan`, `maria`, …).
ЗАПИСИ ОДНОГО ДИКТОРА — ВСЕГДА ОДИН СПЛИТ (train ИЛИ test), иначе
нарушится speaker-disjoint и метрики станут фиктивными. 2–4 диктора
отложите целиком в `--split test` (тестовые дикторы, которых модель не
видела при обучении) — по одному на каждый из трёх языков, обязательно.

## 2. Позитивы — фраза «Omni»

Записывайте так, как реально будет использоваться wake-word:

- **дистанция 0.5–3 м** (телефон на столе или в руке — не у рта);
  для носимого — обычный ношной сценарий (ухо/подбородок), см. §4;
- разная громкость и интонация: обычная речь, шёпот, вопрос, из другой
  комнаты; утром/вечером (голос меняется);
- варианты фразы: «omni», «омни», «omni, …», «hey omni», «omni are you
  there» — каждое произнесение отдельным файлом;
- **пауза ≥1 с до и после** фразы; обрезка не нужна — скрипт проверит
  длительность (0.3–3.0 с бракуется/принимается автоматически);
- удобно: 50 фраз за подход, файлы нумеруются диктофоном сами;
- НЕ используйте громкую связь/диффузор при записи позитивов (эхо фразы
  в микрофон фальшивит данные).

Экспорт из диктофона: **WAV** (m4a/ogg скрипт не читает). 16 кГц mono
идеально; любое разрешение конвертируется автоматически.

## 3. Акустическая матрица (обязательная)

Каждый сценарий даёт СВОЮ долю и позитивов, и фонов. Цель — ≥20%
позитивов и ≥20% фоновых часов из каждого сценария (кроме тихой комнаты —
остаток):

| # | Сценарий | Позитивы «Omni» | Фон (длинные записи) |
|---|---|---|---|
| A | Тихая комната (фон. тишина, ~30 дБ) | остаток, довести минимум | ≥1 ч |
| B | Реверберантное помещение (плитка/холл/пустой офис, заметно эхо) | ≥20% | ≥2 ч |
| C | Улица: транспорт (шагом у дороги, поток машин) | ≥20% | ≥2 ч |
| D | Общественное место: разговоры рядом (кафе, офис, гости дома) | ≥20% | ≥2 ч |
| E | Из другой комнаты / 2–3 м, закрытая дверь | ≥20% | ≥2 ч |
| F | Машина (движение, мотор + стекло) — если носимое используется в дороге | по наличию сценария | ≥1 ч |

Фонов — длинные записи (≥30 с, лучше по 5–10 минут) БЕЗ фразы «Omni»
(иначе в фоне будут ложные позитивы при сегментации). Суммарно ≥10 часов
(считаются только файлы ≥30 с).

Особая ценность сценариев C/D: голос рядом — это источник ложных
срабатываний в реальной жизни, а в v0.1 (TTS-синтетика) его нет вообще.

## 4. Сценарии устройств (носимое ≠ телефон)

v0.1 видела «идеальный» микрофон; в поле модель слышит предусилитель
наушников/клипа, ветер, касания. **≥30% позитивов записывать микрофоном
целевого носимого устройства**:

- наушники/клип: встроенная запись устройства (если есть) либо OMNIX
  near-miss захват (§5) на самом устройстве;
- обязательно: надевание/снимание (касания), ветер на улице, разговоров
  на ходу;
- телефон в руке/на столе — оставшийся процент (сравнительная база).

Метку устройства кодируйте в имени файла: `live_<speaker>_earbud_001.wav`,
`live_<speaker>_phone_001.wav` (скрипт не разбирает префиксы — только
`live_<speaker>_`, остаток имени свободно).

## 5. Hard negatives из реальной эксплуатации (near-miss захват)

У v0.1: ~19 ложных/час на adversarial-стриме. Реальные near-miss из
беты — самые ценные негативы (реальный голос, реальный шум устройства).

Механизм есть в коде (PR #113, `NearMissRecorder`): флаг
`WakeWordConfig.nearMissCapture=true` (DataStore `wakeword.*`; в
бете-сборке включается строкой в `SettingsDataStore` или future-UI) →
запись WAV (2.5 с хвост) на кадры со скором ≥0.25, НЕ ставшие детекцией.
Файлы: `filesDir/nearmiss/nm-<epoch>-score<X.YYY>.wav` + `manifest.jsonl`
(время, скор, модель, порог, SNR). Кап 40 МБ, наружу не покидают.

Сбор:
1. Выпустить бету с флагом, попросить 10–20 участников носить устройство
   обычным образом (≥неделя суммарно).
2. `adb pull /sdcard/Android/data/<pkg>/files/nearmiss/`.
3. **Прослушать каждый файл и разметить** (это вручную, ~10 сек/файл):
   - реально сказано «Omni», но не сработало (patience/cooldown/шум) →
     ПОЗИТИВ: `live_<speaker>_nm_<n>_pos.wav` → `--kind positive`;
   - не «Omni» (шум, похожие слова, чужой голос) → ТРУДНЫЙ НЕГАТИВ:
     `hard_nearmiss_<n>.wav` (маркер `hard` в имени — скрипт посчитает) →
     `--kind negative`.
   Манифест подскажет: `score` ≥ `threshold` при `snrDb` в нулях —
   чаще всего «сказано, но не докликнулось».
4. Целевой вклад: ≥50 размеченных near-miss в трудные негативы.

## 6. Негативы (статичный набор)

- обычная речь (разговоры, ТВ, подкасты) — длинные записи до 10 минут;
- **трудные негативы** — отдельно, файл в имени со словом-маркером:
  `hard_many_01.wav`, `honey_02.wav`, `умный_03.wav`, `тони_04.wav`,
  `hard_nearmiss_*.wav` (из §5) — минимум 200 шт; скрипт считает по
  маркерам: `many, money, honey, умн, тон, омн_, hard`;
- фон — по матрице §3.

## 7. Заливка и статус

```bash
# проверка партии без копирования (СНАЧАЛА)
python3 training/collect_live.py add ~/downloads/batch1 \
    --speaker ivan --kind positive --dry

# заливка
python3 training/collect_live.py add ~/downloads/batch1 \
    --speaker ivan --kind positive --split train

# статус датасета против целей v0.2
python3 training/collect_live.py report
```

Скрипт нормализует всё в контракт пайплайна (16 кГц mono int16),
бракует неформат, предупреждает о клиппинге и тишине, ведёт манифест
`training/collect_*.csv`.

## 8. Чеклист партии (прогнать перед `add`)

- [ ] WAV (не m4a/ogg), один диктор в партии;
- [ ] имя файла `live_<speaker>_<device>_<n>.wav`, device ∈ {earbud, phone};
- [ ] пауза ≥1 с до/после фразы; длительность 0.3–3.0 с;
- [ ] громкая связь/диффузор НЕ использовались;
- [ ] диктор уже зафиксирован в train ИЛИ test — не в обоих;
- [ ] `--dry` отработал без брака >10% (больше — переснять);
- [ ] после `add` — `report`, статусы не откатились.

## 9. Приёмка v0.2: оценка на НОВОМ живом тест-наборе

После `report` = «ДИАСЕТ ГОТОВ»:

```bash
python3 training/make_features.py   # аугментация + фичи (живые данные внутри)
python3 training/train_omni.py      # обучение, подбор порога, экспорт ONNX
python3 training/eval_streaming.py  # стриминговый eval
python3 training/verify_model.py --model <onnx>   # контракт перед заменой в APK
```

Метрики — НЕ только на старом синтетическом holdout (jenny/ruslan из
v0.1): обязательна оценка на **новом живом speaker-disjoint тест-сплите**
(2–4 диктора из §1, которых модель не видела). Отчёт (в
`training/OMNI_V0.2_REPORT.md`) должен нести ОБА набора:

| Метрика | Старый синтетический holdout | Новый живой disjoint | Критерий |
|---|---|---|---|
| recall @ 0.35 (стриминг) | регрессия: не хуже 0.90 v0.1 | измеряется | ≥ 0.90 |
| FP на речевых негативах | регрессия: не хуже 3–5% v0.1 | измеряется | ≤ 5% |
| FP/час на adversarial-стриме | регрессия: ≤ ~19 (уровень v0.1) | — | не хуже |

Пройден, если критерий закрыт на ЖИВОМ наборе и регрессия на синтетике
нет. Дальше — полный список критериев фазы 2 (training/README.md):
verify зелёный, прогон `device-validation/06-wakeword-metrics.sh` на
устройстве, обновление NOTICE/SHA256SUMS/`ModelDigests` (пин!) и замена
модели в assets через `WakeWordConfig.modelAssetPath` (фолбэк
`hey_jarvis_v0.1.onnx` — после приёмки).
